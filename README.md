# Сквозной аудит и система мониторинга качества данных: контур приёмки ЕГАИС

Проектная работа по Data Quality: полный цикл от профилирования сырых данных до работающего
мониторинга, Data Contract, разбора инцидента и стратегии внедрения.

**Домен** — государственный учёт оборота алкогольной продукции (ЕГАИС).
**Ракурс** — дата-инженер **контура приёмки**, а не сотрудник подконтрольной организации.
Аудит смотрит внутрь: не «правильно ли организация отчиталась», а **не испортили ли мы сами**
принятые от неё данные по пути от приёмки до витрины, на которой строится контроль рынка.

> Учебная модель контура приёмки на синтетическом датасете (1.9 млн строк), а не описание
> реальной архитектуры ЕГАИС.

## Главный результат

Принятый от организаций поток **целостен**, а витрина контроля — нет:

| Что нашли | Масштаб | Правило |
|---|---|---|
| Операции не доехали до витрины при загрузке | **100 000** (10% потока) | DQ-02 |
| Код организации теряет ведущий ноль (`00123456` → `0123456`) | **90 000** (10% витрины) | DQ-03, DQ-04 |
| Баланс «получено минус списано» не сходится | **96 309** пар из 274 995 (35%) | DQ-14 |
| Ни одна партия не дошла до витрины целиком | все **10 000** партий, в среднем −10 операций из 100 | DQ-02 |
| `bottling_date`, `wbpid` не заполняются ни разу | 100% потока | — (разрыв схемы) |
| Журнал изменений витрины не ведётся | — | gap в Data Contract |

**Два дефекта связаны причинно: второй возник при попытке исправить первый.**

Решающая улика — испорчено ровно **10%** кодов, а не 100%. Баг приведения типа внутри ETL
применяется к каждой строке потока, поэтому такую избирательность объяснить не может: значит
преобразование применялось к выделенному подмножеству строк, отдельно от штатной загрузки.
Реконструкция подтверждается остальными фактами (0 «сирот», 0 дублей, соседние поля совпадают
с источником 1:1, все 90 000 кодов чинятся одним способом, а сумма «потеряно + искажено» стабильно
держится на ≈1 681 операции в день):

1. Загрузка потеряла ≈190 000 операций, равномерно по всему периоду.
2. Дыру заметили частично и **вручную довосстановили 90 000 операций** — выгрузили из приёмки,
   провели через промежуточный инструмент, вставили в витрину.
3. В этом ручном цикле код организации прошёл числовое приведение и потерял ведущий ноль.
4. Оставшиеся 100 000 операций не восстановили, а побочный эффект вставки никто не заметил.

**Правило-сторож DQ-11 такую вставку не ловит** и сегодня зелёное: вставляли реальные операции
из приёмки, «сирот» не возникло. Дефект по существу данных ловит **DQ-14 — баланс перемещения**:
списать по справке Б больше, чем получено, нельзя, поэтому отрицательный баланс прямо указывает
на проблему. По нему же дефекты и разделяются при разборе: из 59 222 несходящихся пар под
корректным кодом **34 195** имеют зеркало под 7-значным кодом (след вставки), а **25 027** его
не имеют (потери загрузки).

Честное ограничение: данные показывают, *что* произошло, но не *кто и когда* это сделал —
журнала изменений витрины нет. Это отдельная находка аудита.

## Данные

PostgreSQL, БД `Project_DQ`:

| Таблица | Строк | Роль |
|---|---|---|
| `public.list_doc` | 1 000 000 | Сырой слой приёмки — операции «как пришли» от 5 000 организаций. **Эталон** |
| `public.doc_oper` | 900 000 | Витрина контроля — **объект аудита** |
| `public.dq_run_history` | 29 | История прогонов пайплайна |
| `public.dq_check_results` | 300+ | Результат каждого правила в каждом прогоне |

**Структура документов и количеств.** Справка А (`form_a` / `doc_1`) сопровождает **партию** от производства
до продажи, справка Б (`form_b` / `doc_2`) — конкретное **перемещение** партии. Оба номера
закономерно повторяются: 10 000 партий по ~100 операций, 200 000 перемещений по ~5 операций,
код продукции един в пределах партии. Поэтому правила проверяют не уникальность справок, а
иерархию (DQ-12) и однородность партии (DQ-13). Количества подчинены балансовой модели:
получатель приходует товар по справке Б и списывает его, поэтому сумма по паре
«организация × справка Б» в приёмке неотрицательна — у 80% пар ровно 0. Структуру задают
`sql/05_regenerate_documents.sql` и `sql/06_regenerate_quantities.sql`.

Маппинг загрузки: `sid→id`, `client_id→org_id`, `oper_date→date_operation`, `doc_type→type_doc`,
`product_id→cod_alco`, `quantity→qua`, `form_b→doc_2`, `form_a→doc_1`;
`doc_id`, `bottling_date`, `wbpid` в витрину не переносятся.

## Запуск

Параметры подключения задаются переменными окружения — **пароля в репозитории нет нигде**:

```bash
cp .env.example .env      # заполнить своими значениями
set -a && source .env && set +a
```

`DQ_PG_PASSWORD` обязателен: без него пайплайн и ноутбук падают сразу, а не подключаются
молча с чужими кредами. В Airflow пароль хранится в Connection `project_dq_postgres`,
в Soda Core — в переменной `SODA_PG_PASSWORD`.

### 1. Подготовка

```bash
pip install psycopg2-binary pandas matplotlib openpyxl soda-core-postgres
psql -h $DQ_PG_HOST -U postgres -d Project_DQ -f sql/03_dq_results_schema.sql   # только при первом запуске
```

> `03_dq_results_schema.sql` пересоздаёт таблицы истории — на живой БД он сотрёт накопленные
> прогоны. Запускать только при первичной установке.

### 2. Правила вручную

```bash
psql -h $DQ_PG_HOST -U postgres -d Project_DQ -f sql/02_dq_rules.sql
```

Вернёт по строке на правило: `rule_id, entity, dimension, total_rows, passed_rows, failed_rows,
pass_rate_pct, threshold_pct, status`.

### 3. DQ-пайплайн

```bash
python checks/dq_pipeline.py --triggered-by manual
```

Прогоняет 14 правил, пишет результат в `dq_run_history` / `dq_check_results` и в `dq_pipeline.log`.
Возвращает **exit code 1**, если провалено хотя бы одно критичное правило (DQ-02, DQ-03, DQ-04,
DQ-11, DQ-14) — этим кодом управляется гейт публикации и алертинг.

### 4. Soda Core

```bash
export SODA_PG_PASSWORD='...'
soda scan -d project_dq -c checks/configuration.yml checks/checks.yml
```

Результат последнего прогона — `checks/soda_scan_output.log`: 17 PASS, 1 WARN (свежесть на
статичном датасете), 4 FAIL. **Вердикт совпадает с SQL-реализацией** тех же правил.

### 5. Airflow

DAG `dq_monitoring_list_doc_doc_oper` развёрнут и работает по расписанию `0 6 * * *` (UTC).
Деплой: скопировать в `<dags_folder>/dq_alko/`, сохранив структуру:

```
<dags_folder>/dq_alko/sql/02_dq_rules.sql
<dags_folder>/dq_alko/checks/{dq_pipeline.py, airflow_dag.py, .airflowignore}
```

Креды — через Airflow Connection `project_dq_postgres` (в коде их нет). Ручной прогон:

```bash
airflow dags test dq_monitoring_list_doc_doc_oper
```

Красный DAG-run на текущих данных — **штатное поведение**: критичные правила падают на дефектных
данных, и таск `gate_downstream_publish` не выполняется, то есть витрина не публикуется в контур
контроля.

### 6. Дашборды

Оба дашборда живут в **Grafana** поверх таблиц `dq_run_history` / `dq_check_results`.

**Технический** — для команды загрузки и DQ: объём данных, полнота обязательных полей, полнота
загрузки, уникальность ключа, сверка кода организации с эталоном, равномерность искажений по
дням и таблица деталей последнего FAIL-прогона. Развёрнут и работает, скриншот —
`dashboard/screenshots/grafana_dq_monitoring.png`. Запросы панелей — `sql/04_grafana_queries.sql`.

**Бизнес-дашборд** — для управления контроля рынка, отвечает на один вопрос: «можно ли доверять
сегодняшним данным?». Модель для импорта — `dashboard/grafana_business_dashboard.json`:

```
Grafana → Dashboards → New → Import → Upload JSON file → выбрать источник PostgreSQL
```

Панели: доля пройденных проверок, три числа (не доехавшие операции, искажённые коды,
несходящиеся поставки), тренд доли операций без дефектов и таблица «что требует внимания»
человеческим языком.

**Алерты** — `dashboard/alerts.yml` (Grafana Unified Alerting): пять правил, разведённых по
severity, с маршрутизацией критичных в дежурный канал.

```bash
sudo cp dashboard/alerts.yml /etc/grafana/provisioning/alerting/
sudo systemctl restart grafana-server
```

### 7. Ноутбук

```bash
jupyter lab notebooks/01_data_profiling.ipynb
```

Ноутбук исполнен на живой БД — все таблицы и графики в нём сохранены вместе с выводом,
поэтому его можно читать и без подключения к базе.

## Что показывает мониторинг сейчас

Последний прогон: **10 из 14 правил пройдено**, красные — DQ-02, DQ-03, DQ-04, DQ-14. Это не сбой
мониторинга, а его работа: пороги заданы от бизнес-требования (≥99%), а не подогнаны под факт,
поэтому реальные дефекты видны, а не спрятаны.

| Метрика | Значение |
|---|---|
| Полнота загрузки | 90.00% при целевых 99% |
| Точность `org_id` | 90.00% при целевых 99% |
| Баланс перемещений (DQ-14) | 64.98% при целевых 99% |
| MTTD без мониторинга | ≈2 734 ч (оценка снизу) |
| MTTD с ежедневным пайплайном | ≤ 24 ч |
| Объём исправления инцидента | 5 000 заявок ≈ 4 190 чел.-ч (очередь ≈16.5 мес на двух операторах) |
| То же при работающем гейте публикации | 0 заявок, 17 чел.-ч |
| Порог окупаемости системы | 142 заявки — 2.8% от одного инцидента |

## Ограничения

- Датасет синтетический и статичный: последняя операция — 2026-08-21, поэтому проверка свежести
  в Soda штатно светится WARN.
- Эффект считается в заявках и человеко-часах, без рублей: число заявок проверяемо запросом,
  спорным остаётся только норматив обработки (он разложен по этапам). Допущение «обратятся все
  5 000 организаций» проверено на чувствительность — вложения окупаются даже при 10%.
- Часть демо-истории прогонов (`triggered_by='backfill_demo'`) смоделирована, чтобы показать
  тренд до внедрения мониторинга; прогоны с `triggered_by IN ('manual','airflow')` — реальные.
